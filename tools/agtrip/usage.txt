This tool provides a shortcut to obtaining prototyping data for use in early
stages of a scrolling game project. It automatically assembles contiguous/
stitched images from a series of overlapping, sequential screen grabs (or
suitably spaced frames from a video capture source / .mp4 video encoding).

===============================================================================
Summary: General Options
===============================================================================

-? -h --help

Help & usage information


-v --verbose

Show more detailed information where relevant


-q --quiet

Suppress all but the most important messages


-wk --wait-key

Don't exit without a keypress - can be useful for debugging if warning messages
are getting lost in batch jobs.


-s --srcseq <file>

Specify filename stub for source frame sequence (extension assumed .png)

This is the numbered sequence of images which will be used to reassemble a
background image.

The images will ideally be arranged such that each is separated by roughly
16-32 pixels. The separation is not strict and may vary. The tool will try
to lock onto changes in separation/step size each frame.

Larger separations will generally result in better removal of sprites, but
more likely to leave holes or lose synclock with the scrolling regions.

Smaller separations will recover background more reliably, but is more
likely to leave sprite traces behind, which will need cleaned up manually
after processing.

Note: Poor spacing, fuzzy source material or too much confusing movement
or large, slow moving sprites can lead to unreliable synclock. The result
will be some frames misinterpreting the scroll rate and becoming merged at
the wrong position - this causes holes and strangely blurred areas in the
final image.

Problems with automatic synclock can be addressed in several ways, either
by narrowing the min/max scroll step via commands, or by making use of a mask
image to 'demote' the synclock importance for fixed parts of the image (This
can help reduce confusion caused by parallax scrolling areas).


-o --outfile <file>

Specify the output filename for the final panorama image (saved as .TGA)


-sm --srcmask <file>

Specify a source mask image to control synclock & pixel integration.

This is a static mask image which is applied to every input frame of the
source sequence. The 'control pixels' are colour-coded to fixed colours with
specific meanings. All other pixel colours are ignored.

MAGENTA (255,0,255)

This pixel colour instructs the tool to A) ignore the pixel during synclock
analysis and B) ignore the pixel when integrating the frames into the final
panorama. i.e. the pixel will be 'transparent' when merged.

This is used to eliminate text and HUD overlays which do not move from one
source frame to the next. If correctly applied, no pixels from these areas
will reach the panorama image and no holes will result in the main part of
the scroll (although some holes can result near the beginning or end of the
panorama which need cleaned up).

GREEN (0,255,0)

This pixel colour instructs the tool to ignore the pixel during synclock
analysis (like MAGENTA) but to keep/merge the pixels regardless.

This is mainly used to 'demote' the importance of parallax scrolling regions
which would otherwise confuse synclock analysis - since there are multiple
scroll rates involved and the tool can't sort them out automatically.

It is best applied as a rectangle in the middle of the primary parallax area.
Don't cover the entire area as it can further confuse the synclock process if
the majority of the input image is masked. It is used only to bias the most
dominant part of the parallax region. Try not to cover any of the primary
scroll region with this colour.


-sb --startbot

Specify the vertical scrolling origin at the bottom of the panorama, with
the viewport panning upwards (typcial for vertical scrolling with progress
being upwards through the game map). 

Otherwise the origin will be assumed at the top, panning downwards. 

If the origin is not set correctly to suit the sequence of input images,
the panorama will not be properly integrated.


-sr --startright

Specify the vertical scrolling origin at the right of the panorama, with
the viewport panning leftwards. This is an uncommon arrangement for
horizontal scrolling maps. The origin is typically on the left, panning
towards the right (default).

See: -sb --startbot for more info.


-pw --panwidth

Set the (conservative) panorama width in pixels. This should be an
over-estimate until the true size is known. The final .TGA will be written
with dimensions no larger than this.


-ph --panheight

Set the (conservative) panorama height in pixels. This should be an
over-estimate until the true size is known. The final .TGA will be written
with dimensions no larger than this.


-mnhs --minhscroll
-mxhs --maxhscroll
-mnvs --minvscroll
-mxvs --maxvscroll

Specify the min and max horizontal/vertical scroll step values between source
frames. This can be used to narrow/restrict or completely override the 
automatic synclock analysis (which tracks the scroll direction & speed).

The default is:

 -framewidth/4  ... +framewidth/4
 -frameheight/4 ... +frameheight/4
 
..where framewidth/frameheight are the dimensions of the input frames.
 
This is often enough for automatic synclock with horizontal or vertical
scrolling in any direction.

If the input material is problematic and fully-automated synclock does not
work (or if the approximate pixel step is known, and you want to speed the
process up), you can specify the real step value range with these switches.

Generally it's better to leave a few pixels of margin so the automated lock
can deal with any scroll speed glitches. This is even more important if the
scroll pauses at any point in the sequence (the bound must then include 0
in the range or the tool will incorrectly deal with the pause)

Note: 

The sign of the step indicates the scroll direction! So for vertical scrolling, 
-minvscroll will be -ve, where -maxvscroll may be anywhere between 0 (for 
stopped/paused scroll) and -minvscroll.


-fxo --framexoff
-fyo --frameyoff

Specify the top-left corner of the active capture rectangle in the source image
sequence. This is provided to remove any border area from the source images.

-fxs --framexsize
-fys --frameysize

These configure the size of the active capture rectangle in the source images.

See: -fxo/-fyo for more info.


-fs --framestart
-fe --frameend

Specify the first and last (inclusive) frame to use from the capture sequence.

Specifying '-fs 2' will begin with image '?_002.png'


-cc --compcurve

Colour error comparison curve for automatic synclock (default=0.25)

This controls the sensitivity to colour error when performing automatic
synclock / scroll tracking.


-ic --intcurve


Colour error curve for competing pixel integration (default=20.0)

This is mainly an internal tweaking value to control the separation of moving
from static content. e.g. the retention of background while removing sprites.

This does not affect synclock but does affect how the synchronised images are
merged into the panorama.
